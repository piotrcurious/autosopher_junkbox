### Autosophers and the next step beyond LLMs: from remembering answers to accumulating knowledge

The important idea in your proposal is not simply to give an LLM a bigger memory. It is to change what the system considers knowledge, how it learns from new information, and whether that learning survives the end of the current conversation.

Your autosopher concept suggests a different division of labor between computation and memory: let neural networks handle perception, ambiguity, language and difficult transformations, while a persistent, explicitly structured associative system stores facts, rules, relationships, domains, maps and discovered results. Unlike a model's internal weights, those structures could be inspected, corrected, extended and shared between different models.

That is a meaningful architectural direction. The most promising version is not a replacement for transformers, but a hybrid system in which an LLM becomes the reasoning interface to a persistent, evolving body of knowledge.

The distinction matters because a model can successfully solve a problem today without retaining the solution tomorrow. An autosopher-based system aims to retain not just the answer, but the reusable structure that made the answer possible.

### 1\. What the original autosopher idea was trying to change

The historical Autosophy work associated with Klaus Holtz dates back to 1974, with later publications describing self-organizing, content-addressable memory structures. The proposal was to replace the conventional division between programmed processing and passive storage with systems whose knowledge structures grow as information is acquired. SCIENCE AND TECHNOLOGY PUBLICATIONS +1

The central difference is the location and form of the learned state.

Conventional neural approach

The model modifies parameters during training. Vast numbers of distributed numerical values collectively encode statistical associations. This is powerful for generalization, but individual facts and relationships are generally difficult to isolate, edit and verify independently.

Autosopher approach

Acquired knowledge becomes an explicitly represented structure. Its nodes, relationships, rules and data can be addressed directly, traversed, amended, tested and saved independently of the process that created them.

Hybrid LLM–autosopher

Neural computation interprets ambiguous evidence, proposes abstractions and develops solutions. Structured memory maintains the evolving knowledge state, while deterministic programs verify calculations, constraints and relationships.

An important qualification: explicit symbolic structures are not automatically intelligent. Conventional databases are parsable, too. The interesting advance is combining explicit, persistent structures with a system that can construct, extend and use them autonomously.

That combination would allow knowledge to grow without requiring every new fact to be absorbed into billions of neural parameters.

### 2\. What your current repository demonstrates

I inspected the code in your [autosopher_junkbox repository](https://github.com/piotrcurious/autosopher_junkbox?utm_source=chatgpt.com). It is useful as a small demonstration of addressable learning, but it is still an early primitive rather than a complete autosopher architecture.

The central implementation has a node containing two integer features, a numeric payload, an outcome, an access counter and two pointers. `autosophy_learn()` inserts a node into a binary search tree or updates the value associated with an existing key; `autosophy_recall()` performs an exact-key lookup. GitHub +1

That provides three useful properties:

* New associations can be added without training epochs or backpropagation.

* The stored records have an inspectable, explicit representation.

* Previously stored associations can be retrieved without asking a neural network to reconstruct them.

But there are important limitations in the actual demonstrations.

The XOR example memorizes a truth table. It inserts the four possible combinations of two binary inputs and their outcomes. It does not discover a general XOR rule or generalize to an unobserved input representation.

The noise detector measures repetition, not truth. A rarely encountered node can be a perfectly correct scientific discovery, while a frequently repeated assertion can be wrong. Your `access_count` is currently updated during learning, and the noise kernel uses that count to distinguish established from infrequent patterns. GitHub +1

The data structure itself is still limited. It is a binary search tree with two integer keys, not a multidimensional associative memory capable of representing arbitrary ontologies, overlapping categories, spatial domains or semantic relationships. It also lacks automatic balancing.

These limitations do not invalidate the direction. They clarify the next research problem: move from exact-address record storage to a general-purpose, self-extending knowledge substrate.

I would treat the repository as a kernel prototype demonstrating explicit online updates, rather than evidence that the broader Autosophy claims have already been proven.

### 3\. Why the combination could be a genuine architectural leap

The relevant question is not whether an autosopher can outperform a neural network at recognizing a pattern. It is whether a system can accumulate a body of reliable, reusable knowledge that improves its performance across many different problems.

Consider an engineering example.

An LLM is given a new map, a ledger of material quantities, equipment specifications and several operating constraints. It must determine whether a proposed design is viable.

A conventional model might perform well, but the information has to be supplied again when the context is lost. A basic RAG system may retrieve the original documents, yet it may not have stored the specific relationships discovered during the analysis.

An autosopher-based system could retain:

* The source documents and their versions.

* The entities, measurements, units and relationships extracted from them.

* The equations and assumptions used in the analysis.

* The derived quantities and their dependencies.

* The constraints that failed, the corrections made and the tests that subsequently passed.

* The reasons a previous approach was rejected.

The next problem can then reuse the verified results rather than repeat the entire discovery process.

This gives the system three different kinds of continuity.

The second property is particularly important. If a material specification changes, a mature system should not merely replace one number in a database. It should identify which calculations, design decisions, reports and downstream conclusions relied on that number.

That is an explicit dependency-management problem, not a problem that requires the LLM to remember every previous conversation.

### 4\. How I would implement it in modern LLMs

I would build an autosopher as a persistent computational service exposed to an LLM through structured tool calls. I would not begin by redesigning the transformer or constructing special hardware.

The initial objective would be to demonstrate that the memory architecture produces a measurable improvement in cumulative problem-solving.

### A. Replace the two-feature node with a typed knowledge model

A general autosopher needs several types of records rather than a single universal node structure.

For example:

```text
Entity
  id
  type
  canonical_name
  attributes

Assertion
  id
  subject
  predicate
  object
  qualifiers
  provenance
  valid_time
  confidence
  version

Rule
  id
  preconditions
  executable_expression
  units_and_types
  validation_tests

Artifact
  id
  type
  content_hash
  schema
  source_reference

Derivation
  id
  input_assertions[]
  rule_id
  output_assertions[]
  execution_result
```

These records form a typed graph, with tree structures and other indexes used where appropriate.

Suppose the system learns:

`Pump A → supplies → Circuit B`

and subsequently records that Circuit B requires a certain minimum flow rate. The relationship is not just text embedded in a document. It is an addressable assertion that can participate in queries, calculations, tests and other relationships.

Crucially, each assertion should identify its evidence, scope and validity. An uncertain hypothesis should not silently become an established fact simply because a model generated it.

### B. Use several complementary forms of associative addressing

One binary search tree cannot efficiently answer every kind of question.

A practical memory system would combine several retrieval mechanisms:

| Mechanism                          | Purpose                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------ |
| Exact identifiers and hash indexes | Retrieve a known entity, record or artifact reliably.                                      |
| Typed graph traversal              | Follow explicit relationships, dependencies and category membership.                       |
| Spatial and temporal indexes       | Retrieve map features, measurements and facts relevant to particular locations or periods. |
| Lexical and vector search          | Locate relevant material when the wording or meaning is approximate.                       |
| Rule and constraint queries        | Find applicable rules, test conditions and derive consequences.                            |

This is where your emphasis on parsable data becomes especially useful.

The vector index can help a model recognize that an imprecise question relates to a known concept. But once the concept is identified, the system can switch to explicit relations and deterministic queries rather than relying on similarity scores to establish facts.

For instance, an approximate semantic search might locate a geological formation. The actual calculation would then retrieve its formal properties, relevant measurements and applicable equations.

The distinction between finding something relevant and establishing something true must remain explicit.

### C. Give the LLM a durable learning loop

This is the heart of the design.

1\. Interpret

LLM parses a question, map, ledger or dataset into structured candidates.

2\. Retrieve and associate

Read existing facts, rules, dependencies, evidence and related artifacts.

3\. Reason and execute

Use the LLM, deterministic code, domain solvers and constraint checks.

4\. Propose new knowledge

Create candidate assertions, rules, derived results and dependency links.

5\. Validate and commit

Check provenance, consistency, constraints and applicable tests; retain unresolved claims separately.

6\. Update the knowledge graph

Persist the accepted knowledge, update indexes and flag dependent conclusions that need recomputation.

Return to step 1 with the enriched memory available.

The LLM would access the service through a small set of tools such as:

```text
memory.resolve(query, filters)
memory.traverse(entity_id, relations, depth)
memory.execute(rule_id, inputs)
memory.propose(assertion)
memory.validate(candidate_id)
memory.commit(candidate_id)
memory.dependencies(assertion_id)
```

This is implementable with current model tool-calling mechanisms, a database and an execution layer.

The important distinction is between proposing an update and committing an update. The LLM can suggest that two previously unrelated entities have a new relationship, but a validator decides whether that relationship is sufficiently supported to enter the trusted knowledge base.

Not every candidate requires a human to approve it. Mechanical checks, independent evidence, executable tests and domain-specific policies can automate much of the validation. High-consequence or ambiguous changes can require stronger evidence or human review.

The result is operational, system-level learning. The base model's weights need not change for the overall system to learn something that remains available in future sessions.

### D. Make updates propagate through the knowledge structure

You specifically describe updating all sections affected by a new discovery. I would implement that with a dependency graph and versioned assertions, not by asking the LLM to search the whole library and edit every mention of a fact.

For example:

```text
Source measurement
       |
       v
Derived material property
       |
       v
Component sizing
       |
       v
System performance
       |
       v
Design decision
```

If the source measurement is corrected, the system identifies the downstream results that depend on it.

It then marks those results as potentially stale and recomputes them where possible. Results that cannot be recomputed automatically remain flagged for review.

This is more reliable than maintaining many independent summaries of the same underlying fact.

It also suggests an essential data-management rule: new knowledge should normally create a new assertion version or an explicit correction event, not destructively overwrite the only copy of the old record. History matters when an older conclusion was valid under an earlier set of assumptions.

### E. Make knowledge portable between models

The shared memory should be model-independent.

Imagine Model A discovers a constraint violation and develops a verified repair procedure. Model B, using different weights and a different context window, later encounters a similar system.

Model B should be able to retrieve:

* The original failure and its conditions.

* The repaired rule or procedure.

* Its test results and scope of applicability.

* The evidence that justified retaining it.

* The circumstances in which the procedure does not apply.

The shared interface should communicate canonical entities, typed relations, data and executable procedures. It should not rely solely on hidden internal activations or embeddings produced by one particular model.

This also means storing verified derivations, tool outputs and useful problem-solving experiences rather than unfiltered conversational transcripts.

The model becomes a replaceable reasoning component. The accumulated knowledge is a separate, durable asset.

### 5\. The hardware question: flash is useful, but not quite in the way proposed

Your memory-bound observation is important. Persistent, explicitly structured knowledge can consume substantial storage, particularly when original documents, alternate versions, provenance and derived artifacts are retained.

Modern flash storage makes a large persistent autosopher practical. However, one hardware detail needs correction.

Conventional NAND flash does not store terabytes in a single physical memory cell. Micron describes triple-level cell (TLC) NAND as storing three bits per cell and quad-level cell (QLC) as storing four. SK hynix has documented 321-layer QLC products with capacities of 1 TB and 2 TB at the device level. Those capacities result from dense arrays of cells and extensive vertical stacking, not from a terabyte of information in each cell. Micron Technology Inc. +1

That distinction does not undermine your proposal. It helps define the practical implementation.

GPU / accelerator

LLM inference, embeddings, parallel numerical operations, visual interpretation and learned transformations.

RAM / high-bandwidth memory

Hot graph nodes, frequently used indexes, query caches, working state and active reasoning data.

NVMe flash / durable storage

Large knowledge graphs, immutable evidence, ontologies, maps, ledgers, historical versions, derivation logs and less frequently used records.

I would use append-oriented updates, batched writes, snapshots and compaction to reduce write overhead. Frequently accessed structures could be cached in RAM, while cold records remain in flash.

This architecture would not require a custom chip at the beginning. It can be prototyped on an ordinary workstation or server, then optimized around observed bottlenecks.

The eventual specialized hardware question is whether graph traversal, associative lookup, constraint evaluation or certain classes of update can be performed closer to storage, reducing data movement between the storage subsystem, CPU and GPU. That is a more concrete target than simply trying to put as much data as possible into each memory cell.

### 6\. Is this really a forgotten direction?

The historical idea has been sidelined in mainstream LLM development, but its component parts have not disappeared.

A notable example is the 2016 Differentiable Neural Computer, which combined a neural network with an external read/write memory and demonstrated structured reasoning tasks involving graph relationships and shortest paths. Nature

More recently, Microsoft's GraphRAG work has combined graph construction, retrieval and LLM-based summarization to support analysis across large collections of text. Microsoft Research

Research published in 2025 and 2026 also directly addresses persistent memory, continual learning and the transition from simply storing an agent's history to extracting reusable experience. ACM Computing Surveys +1

These are related approaches, not evidence that all systems have converged on your proposal.

The remaining architectural gap is that many LLM applications still treat external memory primarily as something to retrieve context from. A stronger autosopher design would make memory a continuously maintained computational structure that the system reads, modifies, tests and uses to build further knowledge.

That is a meaningful distinction, although it needs to be demonstrated experimentally rather than inferred from the name of the architecture.

I would also avoid adopting the strongest claims in early Autosophy literature literally. Shannon's information theory remains valid for describing uncertainty and communication capacity; it was never a complete theory of semantic meaning. An explicit knowledge representation complements information theory rather than proving it false.

### 7\. What could prevent the leap from working?

The main technical challenge is not storage capacity. It is determining what deserves to be stored, what it means, and when it is safe to reuse it.

Incorrect knowledge can become more dangerous when it persists. A hallucinated fact that disappears with a conversation is bad; a hallucinated fact that becomes a trusted rule and influences a hundred later decisions is worse. Provenance, validation and explicit uncertainty must be built into the write path.

Memory growth needs management. Storing everything indefinitely would create a huge, noisy and increasingly expensive structure. The system needs consolidation, deduplication, versioning and policies for retaining or retiring information. Historical evidence should remain available even when a claim is superseded.

Generalization still matters. Exact-key retrieval excels at retrieving known records. It cannot, by itself, infer an unexpected relationship or create a useful abstraction. The neural component remains important precisely because it can identify possible relationships that have never been explicitly stored.

Shared memory creates governance problems. If multiple models can update the same knowledge base, the service needs permissions, transaction control, conflict resolution and mechanisms to protect it from malicious data and prompt-injection attempts embedded in external sources.

These are reasons to develop the architecture as a hybrid system, not reasons to abandon it.

### 8\. The experiment I would build first

I would start with a narrow but demanding benchmark rather than attempting to build a universal autosopher immediately.

Use an engineering dataset containing maps, tabular measurements, explicit constraints and several linked calculations. Give the model a sequence of tasks in which the dataset changes, corrections arrive and later questions depend on earlier discoveries.

Compare four systems:

| System           | What it tests                                                                         |
| ---------------- | ------------------------------------------------------------------------------------- |
| Base LLM         | How much can be solved from the supplied context and existing model knowledge?        |
| Conventional RAG | Does retrieving relevant source material solve the problem?                           |
| GraphRAG         | Does graph-based retrieval improve reasoning across related facts?                    |
| LLM + autosopher | Does persistent, validated, dependency-aware learning improve cumulative performance? |

Measure whether the system retrieves new knowledge correctly, adapts to corrections, avoids stale conclusions, generalizes to new queries, and transfers useful results to another model. Also measure latency, storage consumption and the rate of incorrect persistent updates.

The critical experiment is not whether the autosopher remembers facts. All four systems can be given some form of retrieval. It is whether the system becomes systematically more capable over a sequence of connected problems because it has accumulated verified knowledge and reusable computational structures.

I would evolve your repository along that path: replace the two-integer binary search tree with a typed, persistent graph; add provenance and versioned assertions; implement dependency tracking; and expose the read–propose–validate–commit interface as tools that an LLM can use. Only then would I consider specialized hardware or more elaborate self-assembling memory algorithms.

### The central thesis

Your university analogy captures the ambition well. The important change is not that the professor gains a larger library. It is that the institution can record discoveries, preserve evidence, revise outdated conclusions, reuse successful methods and make the accumulated results available to new researchers.

An autosopher should therefore be more than an external database or a persistent chatbot memory. It should be a durable, structured knowledge environment in which an LLM can participate in the process of acquiring and extending knowledge.

The model supplies flexible reasoning and abstraction. The autosopher supplies continuity, explicit structure and dependable access to what the system has already learned. A validation layer determines which discoveries deserve to become part of the shared record.

The real leap would be from a model that repeatedly performs intelligent acts to a system that accumulates the validated results of those acts and uses them to become more effective over time.
